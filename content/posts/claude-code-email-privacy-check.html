Claude Code was one of the most discussed names in AI this week, and not for a new feature. The story at the top was a user's report that the tool had put their email address into web requests. A second story was about saved permission rules turning up in public repositories. Both are reasons to spend ten minutes checking your own setup, and this guide is those ten minutes: what was reported, what Anthropic changed, what the change leaves open, and three things to do about it.

1. What was reported

On November 5, 2026, a user opened an issue on Claude Code's public repository titled "Privacy violation in User-Agent header". They wrote that Claude Code, version 2.1.318 on macOS, had given their email address to third-party websites in the User-Agent header while it was doing web searches, and that they were now receiving scam email. The User-Agent is the line a program sends to every website it contacts to say what it is.

An Anthropic contributor replied the same day. In their words, Anthropic "introduced a built-in mod called cc-plugin-privacy to deterministically block this behavior in v2.1.317 and later", it is on by default, and it can be switched in /plugins. They asked to be told of any gap.

We did not reproduce the behaviour. What follows relies on what Anthropic itself has published and on tests of our own safeguard.

2. Why an agent would do this

Two facts make this unsurprising.

  • The model is given your address. The README Anthropic published with the block says so directly: "The context hands the model the signed-in account's address to identify the user."
  • Some websites ask for exactly this. Wikimedia's policy for automated clients, for example, asks for a User-Agent that includes "some way of contacting you", and gives the example CoolBot/0.0 (https://example.org/coolbot/; coolbot@example.org). That request is reasonable when a developer writes a bot. It is a problem when an assistant answers it for you with your personal address, without asking.

So the question to ask of any AI tool is not only "what does the company collect?" It is also "what does the tool know about me, and where can it put that?"

3. What the built-in block covers, and what it does not

Anthropic's README is unusually plain about the limits. It describes the block as "a courtesy, not a boundary", and says "it covers one shape".

RefusedNot checked, by the README's own list
A shell command (Bash, PowerShell or Monitor) that contains your account address and names a User-Agent, such as curl -A, wget -U or the words User-AgentThe address with no User-Agent named: in a URL, in a request body, in a From: header, in curl -u
The address in capitals or percent-encodedThe web tools, WebFetch and WebSearch, and all MCP tools
Refused with no prompt, in every permission mode. A saved allow rule does not clear itAn address worked out when the command runs, such as $(git config user.email), a variable, or a script that holds it

It can be turned off with /plugin disable, or by setting "cc-plugin-privacy@builtin": false under enabledPlugins in your user settings. A repository's settings cannot turn it off, which is the right way round: a project you cloned should not be able to remove your protection.

4. Three checks to do now

Check 1: your version

claude --version

You want 2.1.317 or later. If it is older, run claude update. The commands are the same on macOS and Windows.

Check 2: the block is on

Open ~/.claude/settings.json (on Windows, %USERPROFILE%\.claude\settings.json) and look for cc-plugin-privacy@builtin. If the line is absent, your settings have not turned it off. If it says false, remove the line. Inside a session, the plugin menu shows the same switch. This checks your own settings only: the README lists other things that can switch the block off, including a switch on Anthropic's side that is read once per session.

Check 3: see what a request carries

You can watch what any tool sends, without trusting anyone's description. Save this as show_headers.py and run it in one terminal:

"""show_headers.py: print what every request to http://127.0.0.1:8099/ carries."""
from http.server import BaseHTTPRequestHandler, HTTPServer


class Show(BaseHTTPRequestHandler):
    def do_GET(self):
        print(self.requestline)
        print(self.headers, flush=True)
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"ok\n")

    def log_message(self, *args):
        pass


HTTPServer(("127.0.0.1", 8099), Show).serve_forever()

5. Add your own block for the shapes left open

A hook is a script Claude Code runs before a tool call; if the script exits with code 2, the call is stopped and the script's message goes back to the model. This one stops any call that contains one of your addresses, in any tool that can reach the network. It covers three of the gaps in section 3: no User-Agent needed, web tools included, MCP tools included.

Save it as ~/.claude/hooks/block-email.sh and put your own address on the second line:

#!/bin/bash
# PreToolUse on every tool: stop a call that would carry one of your email addresses.
ADDRESSES=("you@example.com")   # put your own addresses here, separated by spaces

INPUT=$(cat)
TOOL=$(echo "$INPUT" | jq -r '.tool_name // empty')

# Tools that only touch local files may mention the address freely.
case "$TOOL" in Read|Edit|Write|Glob|Grep|NotebookEdit) exit 0 ;; esac

PAYLOAD=$(echo "$INPUT" | jq -c '.tool_input // {}' | tr '[:upper:]' '[:lower:]')
for address in "${ADDRESSES[@]}"; do
  plain=$(echo "$address" | tr '[:upper:]' '[:lower:]')
  encoded=${plain/@/%40}
  if [[ "$PAYLOAD" == *"$plain"* || "$PAYLOAD" == *"$encoded"* ]]; then
    echo "Blocked: this $TOOL call contains the email address $address. Run it again without the address. If a site asks for contact details, tell the user and let them decide." >&2
    exit 2
  fi
done
exit 0
chmod +x ~/.claude/hooks/block-email.sh

Register it for every project by adding this to ~/.claude/settings.json. With no matcher, the hook runs before every tool; the script itself lets the file tools through.

{
  "hooks": {
    "PreToolUse": [
      {
        "hooks": [
          { "type": "command", "command": "~/.claude/hooks/block-email.sh" }
        ]
      }
    ]
  }
}

If the file already has other settings, add the hooks block inside the existing braces. Then test it before you rely on it. Save this as test-block-email.sh in the same folder as the hook, make it executable, and run it from that folder:

#!/bin/bash
# Send sample tool calls to the hook and show what it decides.
check() {  # check <expected exit code> <label> <json>
  message=$(echo "$3" | ./block-email.sh 2>&1); code=$?
  [ "$code" = "$1" ] && mark="ok  " || mark="FAIL"
  printf '%s exit %s  %-34s %s\n' "$mark" "$code" "$2" "${message:0:60}"
}

A seat belt, not a wallThe last test passes because the address is not in the command's text; it is fetched when the command runs. No text match can catch that. The hook will also stop harmless local commands that mention your address, such as git config user.email; the model is told why and you can run those yourself. 6. Use an address you can throw away

The lasting fix is to make the address not worth leaking. Sign in to developer tools with an address that is not your main one: an alias your mail provider lets you create, or a separate mailbox. If it starts receiving junk, you know where it came from, and you can replace it. This is our advice, and it applies to every tool that knows who you are, not to one product.

7. The other story: saved permission rules

The second widely shared story was about permission rules ending up in public repositories with secrets inside. We could not read the report itself, so here is what Claude Code's own documentation says, and how to check your repositories.

When Claude Code asks to run a command and you choose "Yes, and don't ask again", it saves that approval as an allow rule in .claude/settings.local.json, at the root of the repository. The file is meant to be personal. The documentation says Claude Code adds it to your global git excludes the first time it writes the file, so it stays out of your commits. It also says that if you created the file by hand, you must add it to .gitignore yourself.

A saved rule contains text from the command you approved. If that text included a key, the key is in the file. Here is an invented example of what to look for; the key is made up:

{
  "permissions": {
    "allow": [
      "Bash(npm test *)",
      "Bash(curl -H \"Authorization: Bearer sk-test-EXAMPLE-not-a-real-key\" https://api.example.com/v1/*)",
      "WebFetch(domain:docs.example.com)"
    ]
  }
}

Run these four checks at the root of each repository. The output is from a sample repository where the file had been committed by mistake:

CommandWhat you want to see
git ls-files …Nothing. Output means the file is tracked.
git log --oneline --all -- …Nothing. Output means it was committed at some point.
grep -nEi …Nothing. Output means a rule holds something that looks like a secret.
git check-ignore -v …A line naming the ignore file that covers it.

If the file is tracked, stop tracking it and ignore it:

Removing the file does not remove the keyAfter that fix, git log --oneline --all -- .claude/settings.local.json still listed the first commit, with the file in it. If a key was ever committed and pushed, treat it as public: replace the key at the service that issued it. Do that first, and tidy the history afterwards if you need to.

Two habits prevent the problem. Do not approve a command with "don't ask again" when the command has a secret written in it; put the secret in an environment variable instead. And look at the saved rules now and then, in /permissions or in the file itself.
