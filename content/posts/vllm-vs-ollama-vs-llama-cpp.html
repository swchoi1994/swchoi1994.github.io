vLLM, Ollama and llama.cpp all do the same basic thing: they load an open-weight model and answer requests in the OpenAI API format. People compare them as rivals, but they were built for different situations, and the right choice usually follows from two questions. Who will use it, and on what hardware?

1. The short answer

Many setups use two of them: Ollama on each developer's laptop, and vLLM on the shared server. Because all three speak the same API, the application code does not change.

4. Where the model files come from

Ollamallama.cppvLLM
Usual sourceIts own model library, by short nameGGUF files, downloaded from Hugging Face with -hfHugging Face repositories, by name
File formatImports GGUF or Safetensors through a ModelfileGGUFSafetensors, with a fallback to the older PyTorch format
QuantizationDoes not quantize GGUF files on import; prepare them firstBuilt in, from 1.5-bit to 8-bit; -hf picks Q4_K_M by defaultRuns pre-quantized models from the Hub

Quantization is why the same model can need very different memory in each tool. A default GGUF download is a 4-bit file, about a third the size of the 16-bit weights that vLLM loads by default. That makes llama.cpp and Ollama far easier to fit on small hardware, at some cost in precision. A fair comparison between tools uses the same precision in each.

5. What happens with several users

This is the real dividing line.

Ollamallama.cppvLLM
Requests at once, by default1 per model; OLLAMA_NUM_PARALLEL raises itA number of slots chosen automatically; -np sets itMany, batched together at every step
When busyQueues up to 512 requests, then answers with 503See its server READMERequests queue; under memory pressure some are paused and redone
Memory cost of parallelismGrows with parallel requests times context lengthThe slots draw on one shared poolA shared cache, sized from free GPU memory
One model across several GPUsNot covered in the pages readNot covered in the pages readYes, with tensor parallelism

Ollama's default of one request at a time per model is right for a personal assistant and wrong for a team. llama.cpp's server enables continuous batching by default and can serve a small group well. vLLM is designed around this problem: its scheduler, its cache and its metrics all exist to keep many requests moving on expensive GPUs.

6. Three defaults that surprise people

The same model can look worse in one toolIf answers seem to forget the start of a long document in Ollama but not in vLLM, the cause is usually the 4,096-token default, not the model. Raise it with OLLAMA_CONTEXT_LENGTH before you compare quality.

None of the three is safe to put on the open internet as installed. Two listen only on the local machine by default, and vLLM's own documentation says not to rely on its API key alone. Put a proxy in front, as in vLLM for a team.

7. One client, three servers

All three accept the OpenAI client. Only the address changes:

from openai import OpenAI

# Pick one base_url:
#   Ollama:     http://localhost:11434/v1
#   llama.cpp:  http://localhost:PORT/v1   (the port the server printed)
#   vLLM:       http://localhost:8000/v1
client = OpenAI(base_url="http://localhost:11434/v1", api_key="not-needed-locally")

reply = client.chat.completions.create(
    model="MODEL_NAME",   # the name each server reports at /v1/models
    messages=[{"role": "user", "content": "Explain a KV cache in one sentence."}],
    max_tokens=100,
)
print(reply.choices[0].message.content)

This is the practical argument for not agonizing over the choice. Write your application against the OpenAI format, start with whichever tool fits your machine today, and move later by changing one line.
